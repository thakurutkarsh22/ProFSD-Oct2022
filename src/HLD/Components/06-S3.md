## 1. What Is S3

Amazon Simple Storage Service (S3) is a **distributed object storage system** launched on **March 14, 2006**. It was one of the first AWS services. Built by a team including Andy Warfield (VP, Distinguished Engineer), it has become the backbone of cloud storage.

S3 is NOT a file system. It is a **flat key-value object store** accessed via REST APIs.

```
Traditional File System:              S3 (Object Storage):

  /home/user/images/photo.jpg         Bucket: my-bucket
  └── Hierarchical directories        Key:    images/photo.jpg
  └── Mutable files (edit in place)   Value:  [Binary blob up to 5 TB]
  └── POSIX semantics (lock, seek)    Metadata: {content-type, etag, custom...}
  └── Single machine / NFS / HDFS     
                                      ✓ Flat namespace (/ in keys is cosmetic)
  ✗ Hard to scale beyond petabytes    ✓ Exabyte scale (350+ trillion objects)
  ✗ Complex replication               ✓ 11 nines durability built-in
  ✗ Expensive at scale                ✓ $0.023/GB/month (Standard)
  ✗ Limited concurrent access         ✓ 100M+ requests/second globally
```

## 3. Storage Engine — ShardStore & Erasure Coding

### ShardStore — S3's Custom Storage Backend

ShardStore is AWS's custom key-value storage engine, written in ~40,000 lines of **Rust**. It won the **Best Paper Award at SOSP 2021**.

```
┌─────────────────────────────────────────────────────────────┐
│                       ShardStore                             │
├─────────────────────────────────────────────────────────────┤
│                                                              │

│  Architecture: LSM-tree variant                              │
│  Deployed: Worldwide, hundreds of PB                         │
│                                                              │
│  ┌─────────────────────────────────┐                        │
│  │         Write Path              │                        │
│  │                                 │                        │
│  │  Incoming shard                 │                        │
│  │       │                         │                        │
│  │       ▼                         │                        │
│  │  ┌──────────┐                   │                        │
│  │  │ WAL      │  (Write-Ahead     │                        │
│  │  │ (append) │   Log for crash   │                        │
│  │  └────┬─────┘   recovery)       │                        │
│  │       │                         │                        │
│  │       ▼                         │                        │
│  │  ┌──────────┐                   │                        │
│  │  │ MemTable │  (in-memory       │                        │
```

### Erasure Coding — How S3 Achieves Durability Without 3x Storage

Instead of storing 3 full copies of every object (300% overhead), S3 uses **Reed-Solomon erasure coding** (typically ~30-50% overhead).

```
┌─────────────────────────────────────────────────────────────────┐
│              ERASURE CODING: 10 + 4 CONFIGURATION               │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Original Object (e.g., 10 MB photo)                            │
│  ┌──────────────────────────────────────────────────┐           │
│  │████████████████████████████████████████████████████│           │
│  └──────────────────────────────────────────────────┘           │
│                          │                                       │
│                    Split into K=10 data shards                   │
│                          │                                       │
│                          ▼                                       │
│  DATA SHARDS (each 1 MB):                                       │
│  ┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐ │
│  │ D1 ││ D2 ││ D3 ││ D4 ││ D5 ││ D6 ││ D7 ││ D8 ││ D9 ││D10│ │
│  └────┘└────┘└────┘└────┘└────┘└────┘└────┘└────┘└────┘└────┘ │
│                          │                                       │
│            Reed-Solomon encoding (Galois Field GF(2^8))         │
│            using Vandermonde matrix multiplication               │
│                          │                                       │
│                          ▼                                       │
│  PARITY SHARDS (M=4 computed mathematically):                   │
│  ┌────┐┌────┐┌────┐┌────┐                                      │
│  │ P1 ││ P2 ││ P3 ││ P4 │                                      │
│  └────┘└────┘└────┘└────┘                                      │
│                                                                  │
│  DISTRIBUTION across AZs:                                       │
│                                                                  │
│  AZ-1 (us-east-1a)    AZ-2 (us-east-1b)    AZ-3 (us-east-1c) │
│  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐ │
│  │  D1, D2, D3     │  │  D4, D5, D6, D7 │  │  D8, D9, D10   │ │
│  │  P1             │  │  P2, P3          │  │  P4             │ │
│  └─────────────────┘  └─────────────────┘  └─────────────────┘ │
│                                                                  │
│  RECOVERY:                                                      │
│  • Need ANY 10 of 14 shards to reconstruct the full object     │
│  • Can tolerate up to 4 simultaneous shard losses               │
│  • Even if an entire AZ goes down → still recoverable          │
│                                                                  │
│  STORAGE MATH:                                                  │
│  • 3x Replication: 10 MB × 3 = 30 MB (200% overhead)          │
│  • Erasure coding:  10 MB + 4 MB = 14 MB (40% overhead)        │
│  • At exabyte scale, this saves BILLIONS of dollars/year        │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### Reed-Solomon Math (Simplified)

```
The encoding uses a Generator Matrix (Vandermonde):

    ┌                    ┐     ┌──────┐     ┌──────┐
    │ 1  0  0  ...  0    │     │  D1  │     │  D1  │  ← Identity rows
    │ 0  1  0  ...  0    │     │  D2  │     │  D2  │    (data pass-through)
    │ 0  0  1  ...  0    │  ×  │  D3  │  =  │  D3  │
    │ ...               │     │  ... │     │  ... │
    │ 0  0  0  ...  1    │     │  D10 │     │  D10 │
    │─────────────────── │     │      │     │──────│
    │ 1  1  1  ...  1    │     │      │     │  P1  │  ← Parity rows
    │ 1  2  4  ...  2^9  │     │      │     │  P2  │    (computed via
    │ 1  3  9  ...  3^9  │     │      │     │  P3  │     Galois Field
    │ 1  4  16 ...  4^9  │     │      │     │  P4  │     arithmetic)
    └                    ┘     └──────┘     └──────┘

All arithmetic uses XOR-based Galois Field operations (GF(2^8)):
  • No floating point → no precision issues
  • XOR is reversible → enables recovery
  • Hardware-acceleratable (SIMD instructions)
```

## 4. How 11 Nines of Durability Actually Works

99.999999999% durability means: if you store **10 million objects**, you might lose **one object every 10,000 years**.

```
┌─────────────────────────────────────────────────────────────────┐
│           THE 5 PILLARS OF S3 DURABILITY                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. ERASURE CODING (primary defense)                            │
│     • Data survives loss of any 4 of 14 shards                 │
│     • Spread across 3+ Availability Zones                       │
│     • Each AZ = separate building, power, network               │
│                                                                  │
│  2. CONTINUOUS INTEGRITY CHECKING                               │
│     ┌──────────────────────────────────────────────────┐        │
│     │  Background "scrubber" processes continuously:    │        │
│     │                                                    │        │
│     │  For each shard on each disk:                     │        │
│     │    1. Read shard from disk                        │        │
│     │    2. Compute checksum                            │        │
│     │    3. Compare with stored checksum                │        │
│     │    4. If mismatch → mark corrupt → trigger repair │        │
│     │                                                    │        │
│     │  Also checks: disk SMART data, latency anomalies  │        │
│     └──────────────────────────────────────────────────┘        │
│                                                                  │
│  3. AUTOMATIC REPAIR (self-healing)                             │
│     • Detect degraded shard count → re-encode from remaining    │
│     • Place new shard on healthy node in different fault domain │
│     • Race against time: repair before more shards fail         │
│     • S3 maintains free space across fleet for fast repair      │
│                                                                  │
│  4. CHECKSUM ON EVERY OPERATION                                 │
│     ┌──────────────────────────────────────────────────┐        │
│     │  Client SDK → computes Content-MD5                │        │
│     │  Network transfer → TCP checksums                 │        │
│     │  S3 frontend → verifies Content-MD5               │        │
│     │  Storage write → computes storage checksum        │        │
│     │  Every read → re-verifies checksum                │        │
│     │                                                    │        │
│     │  2024: Additional checksums supported:            │        │
│     │  CRC32, CRC32C, SHA-1, SHA-256                    │        │
│     └──────────────────────────────────────────────────┘        │
│                                                                  │
│  5. HARDWARE FAILURE ISOLATION                                  │
│     • Disks across different racks, power domains, AZs          │
│     • Correlated failures (e.g., firmware bug) handled by       │
│       distributing shards across hardware cohorts               │
│     • Entire AZ failure → still recoverable                     │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### Durability vs. Availability — They Are NOT the Same

```
┌────────────────────────────────────────────────────────────────┐
│                                                                 │
```

## 5. Consistency Model — From Eventual to Strong

### The Journey (2006 → 2020)

```
TIMELINE:
═══════════════════════════════════════════════════════════════════

2006 ─── S3 launches with EVENTUAL consistency
         │
         │  Problem: PUT new object → immediate GET could return 404
         │  Problem: DELETE object → immediate GET could still return it
         │
         ▼
2006-2020  WORKAROUNDS ERA:
         │
         │  • EMRFS Consistent View (for EMR + S3)
         │  • S3Guard (DynamoDB as consistency layer)
         │  • Application-level retries with exponential backoff
         │  • "Read your own writes" flags in app layer
         │
         ▼
Dec 2020 ─── STRONG READ-AFTER-WRITE CONSISTENCY (free, automatic)
              │
              │  ✓ PUT new object → immediate GET returns it
              │  ✓ Overwrite object → immediate GET returns new version
              │  ✓ DELETE object → immediate GET returns 404
              │  ✓ LIST immediately reflects changes
              │  ✓ No performance penalty
              │  ✓ No additional cost
              │  ✓ No application changes needed

═══════════════════════════════════════════════════════════════════
```

### How Strong Consistency Works Internally

```
┌─────────────────────────────────────────────────────────────────┐
│            S3 STRONG CONSISTENCY IMPLEMENTATION                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Two key subsystems, both must agree:                           │
│                                                                  │
│  ┌─────────────────────┐    ┌─────────────────────────────┐    │
│  │  PERSISTENCE LAYER   │    │  INDEX / METADATA LAYER      │    │
│  │  (actual data bytes) │    │  (object → location mapping) │    │
│  └──────────┬──────────┘    └──────────────┬──────────────┘    │
│             │                              │                    │
│             │                              │                    │
│             ▼                              ▼                    │
│  Shards written to           Metadata committed via             │
│  storage nodes across        CONSENSUS PROTOCOL (Paxos/Raft)   │
│  multiple AZs                across multiple AZ replicas        │
│                                                                  │
│  HOW A PUT ACHIEVES STRONG CONSISTENCY:                         │
│                                                                  │
│  1. Frontend receives PUT request                                │
│  2. Data shards written to storage nodes (quorum write)         │
│  3. Metadata update sent to index service                       │
│  4. Index service runs consensus:                               │
│     ┌───────────────────────────────────────────┐               │
│     │  Leader proposes: "key X → shards [a,b,c]" │               │
│     │  Replica in AZ-1: ACCEPT ✓                 │               │
│     │  Replica in AZ-2: ACCEPT ✓  (majority!)    │               │
│     │  Replica in AZ-3: ACCEPT ✓                 │               │
│     │  → COMMITTED                               │               │
│     └───────────────────────────────────────────┘               │
│  5. Only AFTER consensus commit → return 200 OK to client       │
│                                                                  │
│  HOW A GET IS ALWAYS CONSISTENT:                                │
│  • Read always goes through the index service                   │
│  • Index service returns the latest committed value             │
│  • No stale reads possible (linearizable)                       │
│                                                                  │
│  INSIGHT from Werner Vogels:                                    │
│  "We didn't sacrifice performance for consistency.              │
│   The consistency was already there in the persistence path.    │
│   We just needed to make the caching layer aware of it."        │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### Cross-Region Replication (CRR)

```
┌───────────────────────────────────────────────────────────────────┐
│                CROSS-REGION REPLICATION                            │
├───────────────────────────────────────────────────────────────────┤
│                                                                    │
│  us-east-1                              eu-west-1                 │
│  ┌──────────────┐                       ┌──────────────┐          │
│  │  Source       │   Async replication   │  Destination │          │
│  │  Bucket       │ ════════════════════▶ │  Bucket      │          │
│  │              │   (typically <15 min) │              │          │
│  │  app-data    │                       │  app-data-eu │          │
│  └──────────────┘                       └──────────────┘          │
│                                                                    │
│  Replicates:                                                      │
│  ✓ New objects (after rule creation)                              │
│  ✓ Metadata changes                                              │
│  ✓ Encrypted objects (SSE-S3, SSE-KMS with opt-in)               │
│  ✓ Delete markers (optional)                                     │
│                                                                    │
│  Does NOT replicate:                                              │
│  ✗ Objects that existed before the rule                           │
│    (use Batch Replication for those)                              │
│  ✗ Objects in Glacier/Deep Archive classes                        │
│  ✗ Server-side encrypted with SSE-C                              │
│                                                                    │
│  Requirements:                                                    │
│  • Versioning must be enabled on BOTH buckets                     │
│  • IAM role with replication permissions                          │
│  • Can be cross-account (different AWS accounts)                  │
│                                                                    │
│  USE CASES:                                                       │
│  • Disaster recovery                                              │
│  • Compliance (data sovereignty)                                  │
│  • Latency reduction (serve from nearest region)                  │
│  • Aggregation (multiple sources → one destination)               │
│                                                                    │
└───────────────────────────────────────────────────────────────────┘
```

## 13. When S3 Couldn't Cope — Limitations & Edge Cases

```
┌─────────────────────────────────────────────────────────────────┐
│        SCENARIOS WHERE S3 HITS ITS LIMITS                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. HIGH-FREQUENCY SMALL OBJECT WRITES                          │
│  ────────────────────────────────────────                       │
│  Scenario: IoT system writing 100K tiny (1 KB) events/sec      │
│  Problem:  Per-prefix limit is 3,500 PUT/s                      │
│            Even with 30 prefixes = 105K PUT/s                   │
│            Each PUT has ~100ms overhead → latency kills          │
│  Better:   Batch events → write one 1 MB object per second     │
│            Or use Kinesis Data Firehose → auto-batches to S3    │
│                                                                  │
│  2. LOW-LATENCY RANDOM READS (< 10ms)                          │
│  ────────────────────────────────────────                       │
│  Scenario: Real-time API serving user profiles from S3          │
│  Problem:  S3 Standard first-byte latency is 100-200ms         │
│            Cannot serve sub-10ms reads                          │
│  Better:   Redis/ElastiCache for hot data                       │
│            S3 Express One Zone for <10ms (but single AZ)        │
│            DynamoDB for consistent single-digit ms              │
│                                                                  │
│  3. APPEND / MODIFY IN PLACE                                    │
│  ────────────────────────────────────────                       │
│  Scenario: Log system that appends lines to a file              │
│  Problem:  S3 objects are IMMUTABLE. Any change = full rewrite  │
│            Append 1 line to 1 GB file = re-upload 1 GB          │
│  Better:   Use EFS, EBS, or write new objects per time window   │
│                                                                  │
│  4. DIRECTORY-STYLE OPERATIONS                                  │
│  ────────────────────────────────────────                       │
│  Scenario: "Rename folder" with 1M objects underneath           │
│  Problem:  No folders exist. Must COPY + DELETE every object.   │
│            1M objects × 2 operations = 2M API calls             │
│  Better:   Design key schema to avoid renames                   │
│            Use S3 Batch Operations for bulk moves               │
│                                                                  │
│  5. POSIX FILE SYSTEM SEMANTICS                                 │
│  ────────────────────────────────────────                       │
│  Scenario: Legacy app using fopen(), fseek(), flock()           │
│  Problem:  S3 has no file locks, no byte-range writes,          │
│            no atomic rename, no hard links                      │
│  Better:   EFS (NFS), FSx (Lustre/Windows), or local EBS       │
│                                                                  │
│  6. LISTING MILLIONS OF OBJECTS QUICKLY                         │
│  ────────────────────────────────────────                       │
│  Scenario: List all 50M objects in a bucket                     │
│  Problem:  LIST returns max 1,000 objects per call              │
│            50M objects = 50K API calls (sequential pagination)  │
│            Could take 30+ minutes                               │
│  Better:   S3 Inventory (daily/weekly CSV/Parquet of all keys)  │
│            Maintain your own index in DynamoDB                   │
│                                                                  │
│  7. STRONG CONSISTENCY ACROSS REGIONS                           │
│  ────────────────────────────────────────                       │
│  Scenario: Write in us-east-1, read immediately in eu-west-1    │
│  Problem:  Cross-region replication is ASYNC (~15 min+)         │
│            Strong consistency is WITHIN a region only            │
│  Better:   DynamoDB Global Tables (cross-region consistency)    │
│            Or accept eventual consistency across regions         │
│                                                                  │
│  8. COST AT MASSIVE EGRESS                                      │
│  ────────────────────────────────────────                       │
│  Scenario: Serving 500 TB/month of video to users globally      │
│  Problem:  $0.09/GB egress × 500 TB = $45,000/month just       │
│            for data transfer (plus storage + requests)           │
│  Better:   CloudFront (reduced egress rates)                    │
│            Cloudflare R2 (zero egress fees)                     │
│            Own CDN (if at Netflix/Dropbox scale)                 │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 14. Anti-Patterns That Kill S3 Performance

```
┌─────────────────────────────────────────────────────────────────┐
│              S3 ANTI-PATTERNS                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ❌ ANTI-PATTERN 1: Sequential Key Names                        │
│  ─────────────────────────────────────                          │
│  BAD:  2024-01-01/log001.json                                   │
│        2024-01-01/log002.json                                   │
│        2024-01-01/log003.json                                   │
│  WHY:  All land on same partition → hot spot                    │
│  FIX:  Add hash prefix: a3f2/2024-01-01/log001.json            │
│        Or reverse the key: nosj.100gol/10-10-4202               │
│                                                                  │
│  ❌ ANTI-PATTERN 2: Polling for Changes                         │
│  ─────────────────────────────────────                          │
│  BAD:  while(true) { listObjects("prefix/"); sleep(5); }       │
│  WHY:  Expensive LIST calls, delayed detection, wastes QPS     │
│  FIX:  Use S3 Event Notifications → Lambda/SQS/EventBridge     │
│                                                                  │
│  ❌ ANTI-PATTERN 3: Millions of Tiny Objects                    │
│  ─────────────────────────────────────                          │
│  BAD:  1 JSON event = 1 S3 object (500 bytes each)             │
│  WHY:  PUT overhead per object, listing nightmare, cost         │
│  FIX:  Batch into larger objects (1-100 MB each)               │
│        Use Kinesis Firehose for auto-batching                   │
│                                                                  │
│  ❌ ANTI-PATTERN 4: Not Cleaning Multipart Uploads              │
│  ─────────────────────────────────────                          │
│  BAD:  Failed uploads leave incomplete parts in S3              │
│  WHY:  You're paying for storage of invisible partial objects   │
│  FIX:  Lifecycle rule: AbortIncompleteMultipartUpload Days=7   │
│                                                                  │
│  ❌ ANTI-PATTERN 5: Public Buckets                              │
│  ─────────────────────────────────────                          │
│  BAD:  Bucket policy with Principal: "*"                        │
│  WHY:  One misconfiguration → data breach (Capital One)         │
│  FIX:  Enable "Block Public Access" at account level            │
│        Use presigned URLs for controlled sharing                │
│                                                                  │
│  ❌ ANTI-PATTERN 6: Using S3 as a Database                      │
│  ─────────────────────────────────────                          │
│  BAD:  Read JSON from S3, modify, write back                    │
│  WHY:  No atomic updates, no transactions, race conditions      │
│        100ms+ latency per operation                             │
│  FIX:  Use DynamoDB, RDS, or Redis for transactional data      │
│        S3 is for blobs, not records                             │
```

### Q10: How would you implement erasure coding? What happens when a disk fails?

**Expected Answer:**

**Encoding:**
- Use Reed-Solomon codes with generator matrix (Vandermonde)
- Split object into K data shards
- Compute M parity shards using Galois Field GF(2^8) arithmetic
- Total N = K + M shards, can tolerate up to M failures
- XOR-based math → hardware-acceleratable (SIMD)

**On disk failure:**
1. Monitoring detects disk SMART warnings or I/O errors
2. Mark all shards on that disk as "degraded"
3. For each affected object: read remaining K healthy shards
4. Reconstruct missing shards via erasure decode
5. Place new shards on healthy disks in different fault domains
6. Update metadata service with new shard locations

**The race condition:**
- Must repair before additional failures reduce shard count below K
- S3 maintains free space across fleet for high-throughput parallel repair
- Repair is prioritized by object health (fewer remaining shards = higher priority)

**Trade-off:** K=10, M=4 (tolerate 4 failures, 40% overhead) vs K=6, M=3 (tolerate 3, 50% overhead)

### Q11: How does S3 handle hot partitions? What if one key gets 100K reads/sec?

**Expected Answer:**

**The problem:** Single prefix limited to 5,500 GET/sec

**How S3 handles it internally:**
- Auto-partitioning: S3 monitors request rates and splits partitions
- But this is reactive and gradual (not instant)
- During the scaling period, clients get 503 Slow Down errors

**What you should do:**
1. **CloudFront in front of S3** — cache hot objects at edge (best solution)
2. **Request hedging** — on 503, retry to different prefix copy
3. **Key distribution** — shard the hot key: `hash(request_id) % N` as prefix
4. **Application caching** — Redis/Memcached for frequently accessed objects
5. **S3 Express One Zone** — 2M GET/sec per directory bucket

**Netflix pattern:** Static assets (posters, artwork) always served via CDN, never direct S3 hits.

### Q13: Explain how S3's strong consistency works without sacrificing performance.

**Expected Answer (Werner Vogels insight):**

The key insight is that S3 didn't ADD consistency — it REMOVED the inconsistency.

**Before 2020:**
- Data writes were already durable (consensus-based)
- But the caching/indexing layer could serve stale reads
- The caching layer was optimized for throughput, not consistency

**The fix:**
- Made the cache layer consistency-aware
- Every write commits to the metadata service via consensus (Paxos/Raft)
- Reads go through the same metadata service, which always returns the latest committed state
- The consensus write was already on the critical path (for durability)
- So making reads go through it added no extra latency

**Why no performance penalty:**
- The consistency mechanism was already there for durability
- They just needed to ensure reads always hit the consistent view
- Caches were updated to invalidate on writes, not serve stale data
- No extra network hops or coordination added

### Q17: A customer reports data corruption in S3. Walk through your investigation.

**Expected Answer:**

```

  • Download the object, compute checksum
  • Compare with ETag (MD5 for non-multipart, or custom checksum)
  • If multipart: ETag is NOT the content MD5 (it's hash-of-hashes)
  • Use additional checksums (CRC32C, SHA-256) if configured

  • CloudTrail: who last wrote/modified this object?
  • Was there a PUT/COPY that overwrote the object?
  • Check if lifecycle rules moved it between storage classes

  • Was Content-Encoding (gzip) applied but not decoded?

  • Verify TLS was used (no MITM)
  • Check for proxy/WAF that might modify content

STEP 5: IF TRUE S3-SIDE CORRUPTION (extremely rare)
  • S3's erasure coding + checksums make this nearly impossible
  • Contact AWS Support with:
    - Bucket name, object key, version ID
    - Expected vs actual checksum
    - Timestamps of upload and download
  • AWS can check shard integrity internally

REALITY: In 99% of cases, "S3 corruption" is:
  • Application bug (wrong upload, wrong encoding)
  • Overwritten by another process
  • Missing Content-MD5 validation on upload
```
